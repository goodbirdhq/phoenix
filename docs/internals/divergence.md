# Divergence from upstream

Phoenix is T3 Code (`pingdotgg/t3code`) with a different face. **Upstream owns the engine**: the
server, orchestration, providers and their harnesses, contracts and protocol, packaging machinery,
and the relay. Its code quality and breadth will outpace ours, so we take its engine as it comes.
**Phoenix owns presentation and workflow**: the sidebar, rows, avatars, footer, palette, identity,
how child sessions are shown, and how a user works day to day. Phoenix changes the engine only when
a Phoenix workflow feature genuinely needs it, and then as a small additive extension that upstream
code never has to know about. Every rule here serves one goal: merging from upstream stays cheap for
years.

`scripts/upstream-divergence.ts` holds the exact path prefixes and is the source of truth; this
table summarises them. Naming rules (which identifiers diverge and which stay upstream's) live in
[Branding](./branding.md).

"Take upstream" means upstream's version of the file wins and the Phoenix change is applied to it
again, adapted to whatever upstream changed. It does not mean dropping the Phoenix change. "Keep
Phoenix" means our file wins, and an upstream fix or feature in it is ported deliberately, not lost.

## Register

One row per divergence. **Engine** marks rows that change upstream-owned behaviour, naming the layer
when only part of one is touched; those are the rows to keep small, additive, and justified.

`node scripts/upstream-divergence.ts [upstream-ref]` checks this table against the tree. It reads
the backticked paths in the Where column (a file covers its tests, a trailing `/` covers a
directory) and reports any upstream-owned file that differs from the merge base without a row.
Files whose every changed line is a rename to a Phoenix name, port, or home count as Identity and
need no listing.
